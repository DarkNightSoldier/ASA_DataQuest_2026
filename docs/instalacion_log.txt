HISTORIAL DE PROBLEMAS ENCONTRADOS Y RESUELTOS (orden cronológico, resumen)
Los logs completos de compilación (varios MB de salida de gcc) no se
versionan aquí por tamaño; este resumen conserva el diagnóstico y la causa
real de cada fallo, con referencias a SETUP.md para la receta exacta.
-----------------------------------------------------------------------------

1. "units"/"sf"/"terra" fallaban con Ncpus > 1 aunque las librerías del
   sistema (sysdeps-r) sí estaban. CAUSA: con Ncpus > 1, R arma un Makefile
   paralelo para instalar varios paquetes a la vez y ese proceso no propaga
   bien CPATH/PKG_CONFIG_PATH/LIBRARY_PATH a cada sub-proceso. SOLUCIÓN:
   options(Ncpus = 1) para compilar (ver SETUP.md, sección "Importante
   sobre la instalación en paralelo").

2. "s2" (dependencia de "sf") y "RcppParallel"/"nloptr" (dependencias de
   "lme4") fallaban por falta de `cmake` (no hay paquete de sistema sin
   sudo). SOLUCIÓN: cmake instalado como *wheel* de PyPI en un venv
   dedicado, `~/.local/share/r-build-tools` (ver SETUP.md sección 1).

3. "gifski" fallaba por falta de `cargo`/`rustc`. SOLUCIÓN: `rustup`
   instalado en espacio de usuario (`~/.cargo`, `~/.rustup`) con el
   instalador oficial, sin sudo (ver SETUP.md sección 1).

4. "ggbump" y "ggstream" fallaban con "not available for this version of R":
   en realidad fueron ARCHIVADOS de CRAN en nov/dic-2025 por falta de
   mantenimiento (no es un problema de esta máquina). SOLUCIÓN: se
   instalan desde GitHub (davidsjoberg/ggbump, davidsjoberg/ggstream), que
   sigue manteniendo el código.

5. "units", "magick", "av" compilaban bien ("* DONE") pero NO cargaban en
   una sesión nueva de R: `libudunits2.so.0: cannot open shared object
   file`. CAUSA: esas librerías (extraídas sin sudo en ~/.local/opt/
   sysdeps-r) no están en el cache de `ldconfig`, y el .so resultante no
   trae un rpath propio. `Sys.setenv(LD_LIBRARY_PATH=...)` NO sirve para
   esto una vez el proceso de R ya arrancó (el enlazador dinámico de Linux
   fija esa variable una sola vez, al inicio del proceso). SOLUCIÓN:
   incrustar el rpath correcto en cada .so con `patchelf --set-rpath`
   (automatizado e idempotente en R/00_instalar_paquetes.R, sección "4c").
   Mismo problema en "RcppParallel" (dependencia de "dtwclust") con su
   propio libtbbmalloc.so.

6. "av" además fallaba en la COMPILACIÓN: el runtime de ffmpeg instalado en
   el sistema es 8.1.2 pero el único `-dev` del repo de Kali es 9.0.2 (ABIs
   distintas). SOLUCIÓN: se descargó también el RUNTIME 9.0.2 bajo sus
   nombres de paquete nuevos (libavcodec63, libavformat63, libavutil61,
   libavfilter12, libswscale10, libswresample7 -- paquetes DISTINTOS de los
   libavcodec62 etc. ya instalados, así que no se tocó nada del sistema) y
   se extrajeron ambos (runtime 9.0.2 + dev 9.0.2) al prefijo de usuario.
   Los .pc de ffmpeg además traen libdir/includedir grabados a fuego en
   /usr/... (no usan ${prefix}), así que hubo que corregirlos con sed.
   Receta completa en SETUP.md sección 3.1.

7. "ggimage" (vía "gdtools"→cairo) fallaba primero por falta de cabeceras
   de cairo/fontconfig/freetype/pixman/x11/xcb (mismo patrón: -dev sin
   sudo, extraído a sysdeps-r), y LUEGO, tras arreglar eso, fallaba el
   ENLAZADO con "cannot find -lcairo" aunque el -L apuntaba al lugar
   correcto. CAUSA: el paquete -dev de cairo trae `libcairo.so` como un
   symlink SIN VERSIÓN que apunta a `libcairo.so.2`, asumiendo que el
   paquete runtime (que trae ese .so.2 real) está instalado en la MISMA
   carpeta -- cosa que no pasa si solo se extrajo el -dev al prefijo
   aislado. Eran 11 symlinks rotos en total (cairo, cairo-gobject,
   cairo-script-interpreter, fontconfig, freetype, pixman-1, X11,
   xcb-render, xcb-shm, Xext, Xrender). SOLUCIÓN: re-apuntar cada symlink
   roto al .so.N real que YA estaba instalado como paquete runtime del
   sistema (ninguno de estos requirió descargar un runtime nuevo, a
   diferencia de ffmpeg). Receta completa en SETUP.md sección 3.1.
